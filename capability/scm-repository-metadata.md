# Редактирование метаданных репозиториев на SCM

На [SCM-платформах][SCM-PLATFORM-TERM] у репозиториев есть **метаданные** — теги,
топики, custom properties, текстовые описания и другие поля, зависящие от
платформы. Они нужны для **отборов** репозиториев и для **служебной информации**.
Git Herder даёт **единый CLI** для **массового** **добавления**, **изменения** и
**удаления** таких метаданных по [SCM-отбору][repository-selection.md] (в том
числе для одного репозитория как частного случая отбора). Продукт опирается на
**общее ядро** операций и типов метаданных, не зависящее от конкретной SCM, и
допускает **узкоспециализированные** типы и способы управления там, где это
поддерживает отдельная платформа.

**Приоритет:** P1 — прямая реализация [BG-4][bg-4].

## Ключевые сценарии

### Гигиена метаданных команды

**Сценарий:** [ST-2][ST-2] приводит теги, топики, описания и другие метаданные
к целевой схеме на наборе репозиториев продукта или группы.

**Инструменты:** [SCM-отбор][repository-selection.md]; массовое изменение
метаданных; сетевые шаги — [отказоустойчивое выполнение][resilient-network-execution.md].

**Outcome:** единообразие на платформе без ручного обхода UI по каждому
репозиторию.

### Массовая простановка после онбординга

**Сценарий:** [ST-2][ST-2] после появления новых сервисов на SCM задаёт общие
метки и описания для отобранного набора репозиториев.

**Инструменты:** добавление и редактирование метаданных в одном прогоне.

**Outcome:** быстрее достижимы отборы и отчёты, опирающиеся на метаданные.

### Удаление устаревших меток

**Сценарий:** [ST-2][ST-2] снимает устаревшие теги или топики с репозиториев,
попавших под отбор.

**Инструменты:** удаление метаданных; настраиваемая политика при ошибке на
объекте (детали — в спецификации).

**Outcome:** актуальная схема метаданных без точечных правок в UI SCM.

### Платформо-специфичное метаданное

**Сценарий:** [ST-2][ST-2] управляет полем или типом метаданных, доступным
только на одной из поддерживаемых SCM.

**Инструменты:** расширение общей модели **исключением** для платформы; те же
операции добавления, изменения и удаления в рамках capability.

**Outcome:** не нужен отдельный инструмент платформы для редких полей при
сохранении общего стиля CLI.

### Массовая правка разработчиком

**Сценарий:** [ST-1][ST-1] в роли исполнителя обновляет метаданные на отобранном
наборе по заданию команды.

**Инструменты:** тот же массовый CLI, что у [ST-2][ST-2].

**Outcome:** предсказуемый процесс без знания API каждой SCM.

## Границы

### Входит

- **Добавление**, **изменение** и **удаление** метаданных репозитория на SCM в
  **массовом** прогоне по SCM-отбору.
- **Общее ядро** типов и операций; **платформо-специфичные** расширения как
  класс исключений.
- Настраиваемые политики при **ошибке на одном репозитории** из набора (принцип
  настраиваемости — в спецификации).
- Участие в сквозных capability: [профиль][profiles.md],
  [SCM-отбор][repository-selection.md],
  [отказоустойчивое выполнение][resilient-network-execution.md],
  [защита от случайных изменений][operation-preview.md],
  [обратная связь в терминале][terminal-feedback.md],
  [трассировка выполнения][operation-trace.md].

### Не входит

- Семантика **критериев SCM-отбора** по значениям метаданных (фильтра «какие
  репозитории затронуть») — единая модель отбора, детали в спецификации.
- Маппинг типов метаданных на API SCM, имена команд и флагов CLI.
- Правила **слияния vs замены** множественных значений, квоты и права доступа —
  прикладная спецификация или ADR.
- Изменение **содержимого git**, вебхуков и иных сущностей SCM вне метаданных
  репозитория.

## Инварианты и углубление

### Инварианты (меняются редко по смыслу)

- Прогон меняет **только метаданные репозитория** на SCM в заявленном объёме
  операции.
- Целевой набор репозиториев задаётся **явным SCM-отбором** до применения
  изменений.
- Операции общего ядра **одинаковы по смыслу** на поддерживаемых SCM в рамках
  заявленного набора P1.

### Допустимое углубление (меняется чаще)

- Новые общие и платформо-специфичные типы метаданных.
- Дополнительные исходы при частичном успехе без смены класса проблем.

## Не делать здесь

- Не описывать user stories и acceptance criteria — для backlog и
  specifications.
- Не рисовать ArchiMate — для `architecture`.
- Не фиксировать технологические решения — для `ADR`.
- Не ссылаться на architecture, specifications и код — нижние слои ссылаются
  сюда сами ([ссылки только вверх][upward-references]).

## Открытые вопросы

- Минимальный **общий** набор типов метаданных в первой поставке P1 (GitLab vs
  GitHub).
- Политика **best-effort** vs **прервать операцию** при ошибке на объекте;
  **идемпотентность** повторного прогона.
- Входит ли **режим предпросмотра** в первую поставку P1 для этой операции.
