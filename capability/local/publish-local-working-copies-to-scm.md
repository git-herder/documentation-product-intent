# Публикация локальных рабочих копий в SCM

Git Herder позволяет **одной командой** опубликовать на [SCM-платформе](../../../../glossary/terms/scm-platform.md)
набор **локальных рабочих копий**, которые **ранее не были** опубликованы в
целевом SCM (критерий «не опубликована» — класс; детали — в спецификации).
Отбор копий — тот же **локальный отбор**, что для
[массовых локальных git-операций](mass-local-git-operations.md): корень workspace,
критерии, список, интерактивный или автоматический режим — без отдельной модели
отбора.

Для каждой копии из отбора в **массовом цикле** (политика на объект, сетевые
ретраи для шагов API и push):

1. **Создать репозиторий** на SCM, отразив **относительную структуру каталогов**

   workspace в иерархии групп или namespace платформы; **недостающие группы**  
     создаются, если SCM их поддерживает (симметрия с зеркалированием групп при  
     [массовом клонировании](../scm/mass-clone.md), но направление «с диска на платформу»).
2. **Настроить origin** в рабочей копии на URL созданного репозитория.
3. Выполнить **push дефолтной и текущей ветки** копии (как класс; определение дефолтной

   ветки — в спецификации).

**Приоритет:** P0 (GitLab, GitHub) — прямая реализация [BG-5](../../motivation/goals.md#bg-5) для сценария
**первой** публикации.

## Ключевые сценарии

### Первая выкладка набора сервисов

**Сценарий:** [ST-1](../../motivation/stakeholders.md#st-1) разработал или собрал на диске набор репозиториев и
должен впервые разместить их в новой группе на SCM без ручного создания каждого
проекта в UI.

**Инструменты:** [локальный отбор](../platform/repository-selection.md), целевой SCM из
[профиля](../platform/profiles.md) или вызова; создание групп и репозиториев; origin и push;
[отказоустойчивая очередь](../platform/resilient-network-execution.md).

**Outcome:** один запуск вместо цепочки «создать проект → git remote → git push»
для каждой копии.

### Миграция дерева каталогов на SCM

**Сценарий:** [ST-1](../../motivation/stakeholders.md#st-1) переносит существующую локальную структуру
микросервисов на платформу и ожидает, что **вложенность каталогов** на диске
отразится в **группах** SCM там, где платформа это позволяет.

**Инструменты:** отражение структуры workspace в иерархии SCM; создание
недостающих групп.

**Outcome:** предсказуемая организация на платформе, согласованная с локальным
layout.

### Копия с уже настроенным origin

**Сценарий:** [ST-1](../../motivation/stakeholders.md#st-1) публикует копию, у которой уже задан remote `origin`
(устаревший URL, другой хост, черновая привязка).

**Инструменты:** настраиваемая политика **переименования** существующего origin
или **удаления** перед записью нового origin.

**Outcome:** контролируемая смена привязки без неожиданной потери старого remote  
или с явным отказом от него.

### Ошибка на одной копии из набора

**Сценарий:** [ST-1](../../motivation/stakeholders.md#st-1) публикует большой набор; на одной копии сбой API, отказ
push или локальное состояние git не позволяет завершить шаг.

**Инструменты:** политика **best-effort** или **прервать весь прогон**; итоговый
статус отражает ошибки; сетевые сбои — через отказоустойчивую очередь.

**Outcome:** массовая миграция или выкладка без полной остановки из‑за единичного
сбоя — по выбору политики.

### Длительный прогон и безопасность

**Сценарий:** [ST-1](../../motivation/stakeholders.md#st-1) или [ST-3](../../motivation/stakeholders.md#st-3) запускает публикацию десятков копий с
изменяющим эффектом на SCM и в remotes.

**Инструменты:** [предпросмотр](../platform/operation-preview.md), [обратная связь в терминале](../platform/terminal-feedback.md),
[трассировка выполнения](../platform/operation-trace.md).

**Outcome:** видимость объёма работ и аудируемость шагов до и после execute.

## Границы

### Входит

- Массовый цикл по [локальному отбору](../platform/repository-selection.md) для **не
опубликованных** ранее в целевом SCM копий (семантика отбора — в спецификации).
- Создание репозиториев и **недостающих групп** на SCM с сохранением структуры
каталогов workspace.
- Настройка origin и **первый** push дефолтной ветки.
- Настраиваемые политики: **существующий origin**,
**ошибка на объекте** (не сеть).
- Сквозные capability: [профиль](../platform/profiles.md), [отказоустойчивое выполнение
сетевых шагов](../platform/resilient-network-execution.md), [предпросмотр](../platform/operation-preview.md),
[терминал](../platform/terminal-feedback.md), [трассировка](../platform/operation-trace.md).

### Не входит

- Повторный Push в **уже существующие** на SCM репозитории **без** шага создания — класс
операции в [массовом выполнении локальных git-операций](mass-local-git-operations.md).
- [SCM-отбор](../platform/repository-selection.md) как вход (только локальный отбор).
- Массовое клонирование **с** SCM — [mass-clone.md](../scm/mass-clone.md).
- Вебхуки, теги, топики и прочие метаданные beyond создания репозитория.
- Имена команд CLI, поля API, точный маппинг пути → namespace — спецификация.

## Инварианты и углубление

### Инварианты (меняются редко по смыслу)

- Каждая обработанная копия соответствует **одному** создаваемому или
согласованному с политикой репозиторию на SCM из отбора.
- **Локальный отбор** не смешивается с SCM-отбором.
- Целевой SCM и учётные данные — из [профиля](../platform/profiles.md) и вызова (класс).
- Итоговый статус прогона **отражает** ошибки по объектам.
- Сетевые шаги API SCM и push подчиняются **единому принципу** отказоустойчивой
очереди.

### Допустимое углубление (меняется чаще)

- Новые политики при существующем репозитории на SCM или origin.
- Уточнение отражения layout при новых SCM в фазах P1+.
- Passthrough параметров push при первой публикации (класс; детали — в spec).

## Открытые вопросы

- **Корень namespace** на SCM: фиксированная группа vs полное зеркало пути от
корня workspace.
- Нужен ли **passthrough** параметров `git push` при первой публикации или только
дефолтная ветка.
- Согласование политик «уже есть на SCM» с политиками **существующей копии** при
[массовом клонировании](../scm/mass-clone.md) при обратных операциях.
- Согласование политики **ошибка на объекте** с политикой после **исчерпания
ретраев** сети.
