# Массовое выполнение локальных git-операций

Git Herder **одинаково** применяет выбранную **локальную git-операцию** ко всем
рабочим копиям из [локального отбора][repository-selection.md]: корень workspace
(текущий каталог или переданный корень), критерии отбора, явный перечень копий,
интерактивный выбор или автоматический охват всех подходящих — как **классы**
входа (детали — в спецификации). В цикле по каждой копии выполняется одна и та же
операция; при **сетевых** сбоях на шагах, где git обращается к удалённому
репозиторию, действует [отказоустойчивая очередь][resilient-network-execution.md].
Поведение при **ошибке на одной копии** задаётся **настраиваемыми политиками**
(best-effort с отчётом по объектам или прервать весь прогон). Параметры git-операции
передаются **в семантике нативного git** из PATH (ограничения и конфликты с
ключами Git Herder — в спецификации).

Поддерживаемые **классы** операций: обновление копий (pull, fetch), публикация
из копии (push), слияние (merge), переключение ветки (switch), изменяющие
действия над remote (добавление, смена URL, удаление, переименование — как классы
намерений, не как перечень подкоманд здесь).

**Приоритет:** P0 (GitLab, GitHub) — классы обновления копий [BG-6][bg-6],
переключение ветки [BG-8][bg-8]; push в **уже привязанные** к SCM копии — часть
[BG-5][bg-5] (первая публикация — отдельная
[capability][publish-local-working-copies-to-scm.md]).
P1 — управление remote [BG-7][bg-7]; merge — P1 (отдельной бизнес-цели нет;
входит в тот же массовый цикл).

## Ключевые сценарии

### Актуализация набора микросервисов

**Сценарий:** [ST-1][ST-1] держит на диске много рабочих копий и должен регулярно
подтянуть изменения с удалённых репозиториев без ручного обхода каталогов.

**Инструменты:** [локальный отбор][repository-selection.md], массовый pull или fetch;
сетевые шаги — [отказоустойчивая очередь][resilient-network-execution.md];
[обратная связь в терминале][terminal-feedback.md], [трассировка][operation-trace.md].

**Outcome:** один запуск вместо N ручных обновлений; итоговый статус отражает ошибки
и конфликты по копиям.

### Мультирепозиторная поставка

**Сценарий:** [ST-1][ST-1] отправляет изменения из нескольких локальных копий в SCM
в рамках связанной поставки (согласованный набор веток — как класс намерения из
[BG-5][bg-5]).

**Инструменты:** локальный отбор, массовый push; сетевые ретраи; [предпросмотр][operation-preview.md]
при изменяющем эффекте.

**Outcome:** сокращение времени и риска пропуска репозитория при публикации набора.

### Массовое слияние в наборе копий

**Сценарий:** [ST-1][ST-1] применяет одну и ту же операцию слияния (merge) в
нескольких копиях, затрагиваемых фичей.

**Инструменты:** локальный отбор, массовый merge с одинаковыми параметрами на
каждую копию; политика best-effort или прерывание; предпросмотр при необходимости.

**Outcome:** отчёт по конфликтам и ошибкам по каждой копии без ручного обхода.

### Подготовка к работе над фичей

**Сценарий:** [ST-1][ST-1] перед началом работы должен оказаться на нужной ветке
во всём наборе локальных копий.

**Инструменты:** локальный отбор, массовый switch (класс переключения ветки;
допустимость checkout — в спецификации).

**Outcome:** согласованное переключение вместо N ручных переходов между каталогами.

### Выравнивание remotes в наборе

**Сценарий:** [ST-1][ST-1] приводит имена и URL remote к эталону на множестве копий
после миграции хоста или переименования групп.

**Инструменты:** локальный отбор, изменяющие классы операций remote; предпросмотр.

**Outcome:** меньше расхождений remote между копиями одного продукта.

### Тонкая настройка через нативный git

**Сценарий:** [ST-1][ST-1] нуждается в поведении git, которое задаётся параметрами
конкретной подкоманды (глубина, ветка, стратегия — как классы намерений).

**Инструменты:** передача параметров **теми же смысловыми ключами**, что у git из
PATH, в рамках, разрешённых спецификацией.

**Outcome:** гибкость git без дублирования всего CLI git в Git Herder.

### Ошибка на одной копии из набора

**Сценарий:** [ST-1][ST-1] выполняет массовую операцию; на одной копии возникает
ошибка, не устранимая сетевым ретраем (конфликт слияния, отказ push, локальное
состояние репозитория).

**Инструменты:** настраиваемая политика **best-effort** или **прервать весь прогон**;
итоговый статус отражает наличие ошибок.

**Outcome:** поведение согласовано со сценарием (массовый прогон vs жёсткий контроль).

## Границы

### Входит

- Единый **массовый цикл** по копиям из локального отбора для классов: pull,
  fetch, push, merge, switch, изменяющий remote.
- Настраиваемая политика **ошибка на объекте** (не сеть).
- Passthrough семантики параметров нативного git (ограничения — в спецификации).
- Участие в сквозных capability: [профиль][profiles.md], [отбор][repository-selection.md],
  [отказоустойчивое выполнение сетевых шагов][resilient-network-execution.md]
  (pull, fetch, push), [защита от случайных изменений][operation-preview.md]
  (push, merge, switch, remote), [обратная связь в терминале][terminal-feedback.md],
  [трассировка выполнения][operation-trace.md].

### Не входит

- **Первая публикация** локальных копий на SCM (создание репозитория через API,
  настройка origin, первый push) —
  [публикация локальных рабочих копий в SCM][publish-local-working-copies-to-scm.md].
- Массовое **получение** копий с SCM (clone) — отдельная capability.
- Rebase и иные git-команды вне перечисленных классов.
- Имена команд и флагов CLI, алгоритмы ретрая, разрешение конфликтов ключей —
  прикладная спецификация.

## Инварианты и углубление

### Инварианты (меняются редко по смыслу)

- На каждую копию из применённого отбора выполняется **одна и та же**
  git-операция с **одинаковыми** параметрами (в рамках passthrough).
- **Локальный отбор** не смешивается с SCM-отбором.
- Итоговый статус массового прогона **отражает** наличие ошибок по объектам.
- Сетевые шаги перечисленных операций подчиняются **единому принципу**
  отказоустойчивой очереди продукта.

### Допустимое углубление (меняется чаще)

- Новые классы локальных git-операций в том же цикле (без смены модели отбора).
- Уточнение политик при конфликтах merge и отказах push.

## Открытые вопросы

- Приоритет **merge** остаётся P1 или переносится в P0 вместе с switch и push.
- Класс переключения ветки: только switch или также legacy checkout в P0.
- Единый порог [предпросмотра][operation-preview.md] для push, merge, switch,
  remote vs «лёгкие» fetch.
- Согласование политики **ошибка на объекте** с политикой после **исчерпания
  ретраев** сети — одна матрица в spec или раздельные настройки.
