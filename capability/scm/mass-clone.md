# Массовое клонирование из SCM

Git Herder позволяет **одной командой** получить на локальной машине согласованный
набор рабочих копий репозиториев, **отобранных на** [SCM-платформе][SCM-PLATFORM-TERM],
в заданный каталог. При клонировании **сохраняется структура групп**, в которой
репозитории организованы на SCM; в пределах, заданных спецификацией и
возможностями платформы, пользователь может **модифицировать** отображение этой
структуры на диске. Поведение при **уже существующей** рабочей копии и при
**ошибке одного объекта** из набора задаётся **настраиваемыми политиками** (профиль,
вызов; детали режимов — в спецификации). Для управления действиями git продукт
допускает передачу **нативных флагов** в `git clone` (перечень и ограничения —
в спецификации).

**Приоритет:** P0 (GitLab, GitHub) — прямая реализация [BG-1][bg-1].

## Ключевые сценарии

### Онбординг набора сервисов

**Сценарий:** [ST-1][ST-1] или [ST-2][ST-2] подключается к новому продукту или
команде и должен быстро получить все нужные репозитории с SCM на рабочую машину.

**Инструменты:** [SCM-отбор][repository-selection.md], целевой корень на диске,
массовое клонирование; сетевые шаги — через [отказоустойчивую очередь][resilient-network-execution.md].

**Outcome:** один запуск вместо множества ручных `git clone` и переходов между
каталогами; сокращение времени до первой работы с кодом.

### Навигация по структуре, как на SCM

**Сценарий:** [ST-1][ST-1] ожидает, что дерево каталогов на диске отражает группы
и вложенность репозиториев на платформе, чтобы ориентироваться в большом наборе
микросервисов.

**Инструменты:** зеркалирование групповой структуры SCM; при необходимости —
модификация layout в рамках возможностей SCM и спецификации.

**Outcome:** предсказуемая локальная структура, согласованная с организацией на SCM.

### Повторный запуск при частично заполненном каталоге

**Сценарий:** [ST-1][ST-1] повторяет массовое клонирование после прерывания или
когда часть репозиториев уже присутствует на диске по целевому пути.

**Инструменты:** настраиваемая политика при **конфликте с существующей** рабочей
копией (класс проблемы; конкретные режимы — в спецификации).

**Outcome:** контролируемое продолжение или остановка без неожиданного перезаписывания
копий.

### Тонкая настройка git при клонировании

**Сценарий:** [ST-1][ST-1] нуждается в поведении `git clone`, которое задаётся
флагами git (глубина истории, ветка и т.п. — как классы намерений, не как перечень
флагов здесь).

**Инструменты:** passthrough нативных флагов в `git clone` в рамках, разрешённых
спецификацией.

**Outcome:** гибкость git без дублирования всего CLI git в Git Herder.

### Ошибка на одном репозитории из набора

**Сценарий:** [ST-1][ST-1] клонирует большой набор; на одном репозитории возникает
ошибка, не связанная с временной сетью (нет прав, репозиторий удалён и т.п.).

**Инструменты:** настраиваемая политика **best-effort** (продолжить остальные с
отчётом по объектам) или **прервать всю операцию**; итоговый статус отражает
наличие ошибок.

**Outcome:** поведение согласовано с ожиданиями команды и сценарием (массовый
онбординг vs жёсткий контроль).

## Границы

### Входит

- Массовое клонирование по [SCM-отбору][repository-selection.md] в заданный
  локальный корень.
- Сохранение **структуры групп** SCM на диске и класс **модификаций** layout.
- Настраиваемые политики: **существующая рабочая копия**, **ошибка на объекте**
  (не сеть).
- Passthrough флагов в `git clone` (семантика — в спецификации).
- Участие в сквозных capability: [профиль][profiles.md] (дефолты),
  [отказоустойчивое выполнение сетевых шагов][resilient-network-execution.md],
  [защита от случайных изменений][operation-preview.md] (длительная операция,
  порог), [обратная связь в терминале][terminal-feedback.md],
  [трассировка выполнения][operation-trace.md].

### Не входит

- Обновление уже существующих копий (pull/fetch, sync) — отдельные операции
  продукта.
- Имена команд и флагов CLI, маппинг групп SCM на пути, значения политик по
  умолчанию — прикладная спецификация.

## Инварианты и углубление

### Инварианты (меняются редко по смыслу)

- Каждый объект клонирования соответствует **одному** репозиторию на SCM из
  применённого отбора.
- Структура групп SCM **отражается** в локальном layout, если пользователь не
  применил разрешённую модификацию из спецификации.
- Политики «существующая копия» и «ошибка на объекте» **настраиваемы** и не
  подменяют осознанный отбор пользователя.
- Сетевые шаги клонирования подчиняются **единому принципу** отказоустойчивой
  очереди продукта.

### Допустимое углубление (меняется чаще)

- Новые режимы при конфликте с существующей копией.
- Расширение классов модификации layout при поддержке новых SCM.

## Не делать здесь

- Не описывать user stories и acceptance criteria — для backlog и
  specifications.
- Не рисовать ArchiMate — для `architecture`.
- Не фиксировать технологические решения — для `ADR`.
- Не ссылаться на architecture, specifications и код — нижние слои ссылаются
  сюда сами ([ссылки только вверх][upward-references]).

## Открытые вопросы

- Полный **перечень режимов** при уже существующей рабочей копии в P0 (пропуск,
  прерывание всей операции, иное).
- **Ветка** по умолчанию vs явный выбор; shallow и depth — только passthrough в
  `git clone` или отдельные параметры Git Herder.
- Согласование политик **ошибка на объекте** с политикой после **исчерпания
  ретраев** сети — одна матрица в spec или раздельные настройки.
- Запись шагов клонирования и ретраев в [трассировку выполнения][operation-trace.md].
