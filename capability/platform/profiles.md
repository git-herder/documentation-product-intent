# Профили Git Herder

Профили — это именованные, переключаемые контексты работы с [SCM-платформой][SCM-PLATFORM-TERM]:
куда подключаться, от чьего имени и с какими типовыми настройками запускать
операции над репозиториями — без повторного ввода параметров подключения при
каждой команде.

**Приоритет:** P0 (enabler для операций с SCM из [бизнес-целей][goals.md] с
приоритетом P0).

## Ключевые сценарии

### Несколько контекстов работы

**Сценарий:** [ST-1][ST-1] работает с разными инстансами SCM или разными
ролями (работа, личные проекты, отдельный корпоративный GitLab).

**Инструменты:** именованные профили; профиль по умолчанию для системы; выбор
профиля на отдельный вызов продукта.

**Outcome:** переключение контекста одним действием, без ручного повторения
эндпоинта и учётных данных.

### Разные режимы на одном SCM

**Сценарий:** [ST-1][ST-1] на одном инстансе и одной учётной записи ведёт
разные продукты или команды (разные группы, каталоги рабочих копий, типовой
отбор репозиториев).

**Инструменты:** несколько профилей с разными наборами дефолтных параметров
операций Git Herder при том же подключении к SCM.

**Outcome:** профиль изолирует контексты SCM: при работе с разными продуктами на
одном инстансе операции остаются в рамках выбранного контекста, снижая риск
случайно применить изменения не к той группе или набору репозиториев.
Сокращаются трудозатраты на повторение одних и тех же значений параметров,
которые задают этот контекст.

### Проверка конфига перед массовыми операциями

**Сценарий:** [ST-1][ST-1] или [ST-3][ST-3] перед клонированием, синхронизацией
или публикацией хочет убедиться, что профиль настроен верно.

**Инструменты:** проверка профиля — подключение к SCM с безопасным чтением, без
изменения состояния репозиториев на платформе.

**Outcome:** ранняя диагностика неверного доступа, адреса инстанса или прав.

### Управление жизненным циклом профилей

**Сценарий:** [ST-1][ST-1] создаёт, просматривает, изменяет и удаляет профили;
назначает профиль по умолчанию.

**Инструменты:** управление набором профилей и выбором активного контекста
(детали интерфейса — в прикладной спецификации).

**Outcome:** предсказуемая конфигурация на машине разработчика и в OSS-сценариях.

## Границы

### Входит

- Именованные профили как единица «подключение к SCM + дефолты операций».
- Переключение контекста: профиль по умолчанию и выбор профиля на вызов.
- Проверка работоспособности профиля относительно SCM.
- Дефолты параметров операций Git Herder, в том числе отбора; **семантика отбора**
  для массовых операций — в [едином отборе для массовых операций][repository-selection.md].
- Дефолты **политик** массовых операций и сетевого выполнения как класс настроек
  (например, поведение при клонировании — см.
  [массовое клонирование][mass-clone.md]; ретраи и очередь — см.
  [отказоустойчивое выполнение][resilient-network-execution.md]; правки
  метаданных на SCM — см.
  [редактирование метаданных репозиториев][scm-repository-metadata.md]) без
  фиксации значений здесь.

### Не входит

- Формат хранения конфигурации, расположение файлов на диске, имена команд CLI,
  способ хранения секретов — прикладная спецификация.
- Хостинг SCM и выдача учётных записей на стороне платформы.

## Инварианты и углубление

### Инварианты (меняются редко по смыслу)

- Профиль **именован** и однозначно выбирается пользователем.
- Один профиль соответствует **одной учётной записи одного инстанса SCM** и
  может задавать **дефолтные значения** параметров операций; допускается
  несколько профилей на тот же инстанс и ту же учётку с разными дефолтами.
- Параметры подключения к SCM для выбранного профиля **не требуют повторного
  ввода** при переключении (механизм — в спецификации).
- Дефолты профиля **не отменяют** возможность явно задать параметры на
  конкретную операцию (приоритет переопределения — в спецификации).
- Проверка профиля **не меняет** состояние репозиториев на SCM.

### Допустимое углубление (меняется чаще)

- Расширение набора дефолтов в профиле по мере появления новых классов операций.
- Дополнительные исходы проверки профиля (диагностика прав, квот) без смены
  класса проблем.

## Не делать здесь

- Профилирование длительности выполнения операций
- Возможности задания более одного SCM в профиле

## Открытые вопросы

- Какой **минимальный набор дефолтов** входит в профиль в P0: только подключение
  или подключение вместе с отбором, локальным корнем, политиками клонирования и
  сетевых ретраев.
- Поведение при **конфликте** дефолтов профиля и параметров, заданных на вызов.
- Нужно ли когда-нибудь **разделить** capability, если сценарии отбора
  репозиториев станут сложнее модели «подключение + дефолты».
