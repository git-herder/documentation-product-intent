# Отказоустойчивое выполнение массовых сетевых операций

Все массовые **сетевые** шаги Git Herder выполняются через **отказоустойчивую
очередь**: при **сетевых** сбоях продукт может **повторить** попытку, чтобы
массовая операция могла **корректно завершиться** при нестабильном подключении.
Пользователь управляет параметрами ретрая: **число попыток**, **длительность
таймаута**, возможность **запретить ретраи**; при неуспехе после ретраев или при
отключённых ретраях — **настраиваемо** пропустить объект или **прервать всю**
массовую операцию (значения по умолчанию, [профиль][profiles.md], вызов — в
спецификации). Единый принцип распространяется на сетевые шаги массовых команд;
какие классы операций охватываются в **P0**, — в спецификации.

Явное исключение: классы обновления копий (pull, fetch), публикации из копии
(push) и изменяющие действия над remote выполняются одним запуском git и
очередь не используют. Ошибка такого шага сразу подчиняется политике ошибки
на объекте — [массовые локальные git-операции][mass-local].

**Приоритет:** P0 (сквозная для массовых команд с сетевыми шагами).

## Ключевые сценарии

### Нестабильная сеть при массовом клонировании

**Сценарий:** [ST-1][ST-1] клонирует большой набор; соединение кратковременно
обрывается на отдельных репозиториях.

**Инструменты:** очередь с ретраями по сетевым сбоям; настраиваемые попытки и
таймауты.

**Outcome:** меньше ручных перезапусков всего прогона из‑за единичных сетевых
сбоев.

### Корпоративная среда и лимиты

**Сценарий:** [ST-1][ST-1] работает через прокси или упирается в rate limit SCM;
отдельные запросы «падают» по таймауту, хотя операция в целом выполнима.

**Инструменты:** настройка таймаута и числа попыток; единая политика очереди для
сетевых шагов.

**Outcome:** предсказуемое поведение при повторных попытках без смены команды.

### Жёсткий контроль в автоматизации

**Сценарий:** [ST-3][ST-3] или [ST-1][ST-1] в скрипте нуждается в **запрете
ретраев** и немедленном сигнале об ошибке сети.

**Инструменты:** отключение ретраев; политика пропуска объекта или прерывания
всей операции при сетевом неуспехе.

**Outcome:** детерминированное поведение для CI и отладки (non-interactive —
см. [обратную связь в терминале][terminal-feedback.md]).

### Исчерпаны попытки на одном объекте

**Сценарий:** после заданного числа ретраев сетевой шаг для одного объекта всё
ещё неуспешен.

**Инструменты:** настраиваемая политика — **пропустить** объект и продолжить
очередь или **прервать** всю массовую операцию.

**Outcome:** согласованность с ожиданиями best-effort vs fail-fast на уровне
массовой команды.

## Границы

### Входит

- **Модель отказоустойчивой очереди** для массовых сетевых шагов.
- **Ретраи** при классе **сетевых** сбоев (граница «сеть vs фатальная ошибка» —
  в спецификации).
- Настраиваемые параметры: попытки, таймаут, **запрет ретраев**; дефолт
  продукта, [профиль][profiles.md], переопределение на вызов.
- Политика при **неуспехе после ретраев** (или без ретраев): пропуск объекта vs
  прерывание всей операции.
- Единый **принцип** для SCM API и сетевых действий git в рамках массовых
  операций (охват P0 — в спецификации).

### Не входит

- Алгоритм backoff, параллельность воркеров, лимиты нагрузки на SCM — spec / ADR.
- Классификация **не-сетевых** ошибок на объекте и политики skip vs abort для
  них — прикладная спецификация соответствующей операции.

## Инварианты и углубление

### Инварианты (меняются редко по смыслу)

- Сетевые шаги массовых операций **не обходят** общую модель очереди без явного
  исключения. Исключение классов pull, fetch, push и изменяющего remote задано
  выше.
- Ретраи применяются к **сетевым** сбоям, а не подменяют исправление неверных
  параметров или прав доступа.
- Параметры ретрая и политика после неуспеха **настраиваемы** на уровне продукта
  (дефолт, профиль, вызов).
- Запрет ретраев — **поддерживаемый** режим, а не только «бесконечные попытки».

### Допустимое углубление (меняется чаще)

- Расширение перечня массовых операций, использующих очередь в P0 и позже.
- Уточнение классификации ошибок и записи в журнал без смены класса проблем.

## Открытые вопросы

- **Параллельность** очереди (последовательно vs несколько воркеров) и лимиты
  нагрузки на SCM.
- Какие сбои считаются **сетевыми** для ретрая vs **фатальными** без ретрая.
- Полный перечень **классов массовых операций** в P0, подпадающих под очередь.
- Запись в [трассировку][operation-trace.md]: каждая попытка ретрая vs
  агрегированный итог по объекту.
- Поведение при **неинтерактивном** окружении, если политика требует решения
  пользователя.
