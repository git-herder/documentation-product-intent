# Единый отбор для массовых операций

Git Herder даёт **общую модель отбора** для любой массовой операции: пользователь
описывает, **какой набор** репозиториев на [SCM-платформе][SCM-PLATFORM-TERM] или
**какой набор** локальных рабочих копий затронуть, **одинаковым способом** для
всех команд своего класса; утилита **скрывает различия API** SCM за единым
интерфейсом отбора на стороне платформы.

**Приоритет:** P0.

## Ключевые сценарии

### Отбор на SCM без знания API

**Сценарий:** [ST-1][ST-1] задаёт отбор репозиториев на платформе (организация
или группа, шаблон имени, **метаданные** — теги, топики, custom properties,
описания и т.п. — как классы параметров, не как поля API) в форме Git Herder и
запускает разные массовые SCM-операции с **той же** формой отбора.

**Инструменты:** единая модель SCM-отбора для
[массового клонирования][mass-clone.md], [отчёта о репозиториях][scm-repository-reports.md],
[редактирования метаданных][scm-repository-metadata.md] и других массовых команд,
обращающихся к SCM.

**Outcome:** не нужно запоминать эндпоинты и детали API GitLab и GitHub для
типовых задач отбора.

### Отбор локальных рабочих копий

**Сценарий:** [ST-1][ST-1] для синхронизации, переключения веток, публикации,
управления remotes и других **локальных** массовых операций указывает набор
рабочих копий **одним и тем же способом** (корень workspace, список, правила —
как классы, не как отдельные схемы под каждую команду).

**Инструменты:** отдельная, но тоже единообразная модель **локального** отбора
для всех массовых команд над копиями на диске.

**Outcome:** не изобретать новый способ указать «с какими копиями работать» при
каждой новой операции.

### Контекст из профиля

**Сценарий:** [ST-1][ST-1] стартует операцию с дефолтным отбором из
[профиля Git Herder][profiles.md] и при необходимости сужает или уточняет его
параметрами вызова.

**Инструменты:** композиция дефолтов профиля и параметров отбора на команду.

**Outcome:** согласованный контекст между сессиями без повторного ввода тех же
ограничений отбора.

### Смена SCM без смены привычек

**Сценарий:** [ST-1][ST-1] переходит с одной SCM-платформы на другую (в рамках
поддерживаемых фаз продукта) и сохраняет **те же смысловые** параметры отбора,
где платформы это позволяют.

**Инструменты:** переносимая семантика SCM-отбора; исключения только для
платформо-специфичных уточнений.

**Outcome:** снижается порог переноса практик между организациями и хостами SCM.

## Границы

### Входит

- Две подмодели: **SCM-отбор** и **локальный отбор**; параметры не смешиваются
  в одной модели.
- Единообразие отбора **внутри** каждой подмодели для всех массовых команд
  соответствующего класса.
- Семантика «набор целей операции» как обязательный смысловой шаг массовой
  команды.
- Допустимость **платформо-специфичных** параметров отбора как исключения для
  части деталей (большинство частых сценариев — общие для всех SCM).
- **Фильтрация по метаданным репозитория** на SCM: отбор по значениям и
  признакам тегов, топиков, custom properties, описаний и аналогичных полей
  (классы параметров, не имена API).

### Не входит

- Маппинг на API SCM, имена флагов, валидация — прикладная спецификация.

## Инварианты и углубление

### Инварианты (меняются редко по смыслу)

- Для **частых** сценариев SCM-отбор **одинаков по смыслу** на GitLab и GitHub
  в P0.
- Параметры отбора **компонуются** с профилем: дефолты из профиля и
  переопределение на вызов.
- Локальный и SCM-отбор — **разные** контексты параметров; одна команда не
  смешивает обе модели в одном наборе ключей.

### Допустимое углубление (меняется чаще)

- Новые общие параметры отбора по мере появления классов массовых операций.
- Расширение списка платформ при сохранении общего ядра параметров.

## Открытые вопросы

- Поведение **платформо-специфичных** параметров на неподдерживающей SCM
  (ошибка, предупреждение, игнорирование) — в спецификации.
- Минимальный **общий** набор параметров P0 для SCM-отбора и для локального
  отбора.
- Минимальный набор **аналитических** параметров SCM-отбора в P0 (ветка,
  расхождение веток и т.п.) для [BG-2][bg-2] — в спецификации; вывод отчёта —
  [отчёт о репозиториях в SCM][scm-repository-reports.md].
- Набор параметров отбора **по значениям метаданных** в P0/P1 и согласование с
  аналитическими критериями BG-2 — в спецификации.
